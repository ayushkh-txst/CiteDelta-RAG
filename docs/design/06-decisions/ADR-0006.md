# ADR-0006 — Build the indexes, buy Postgres

**Status:** Accepted · **Date:** 2026-08-08

## Context

The spec's thesis is "build the parts other people import, and measure them."
That applies to search and the temporal predicate, not to everything.

## Decision

Write the inverted index, the BM25 ranking, the varint postings encoding, the
bitemporal layer, and the ANN index by hand. Postgres, Docker, `fastembed`, and
eCFR's public API are dependencies — bought, not built.

## Alternatives

- **Import `whoosh`/`SQLite FTS`/`pgvector` outright** — no one interviews
  you on a queue you configured. The thing being demonstrated is the design
  judgment behind a hand-built retrieval layer.

## Consequences

**Positive.** The corpus and the index *is* the deliverable. A hand-built
index plus a conformance oracle running against the same corpus is exactly the
way to be able to whiteboard any piece of it cold.

**Negative.** The defense against "reimplementing infrastructure badly" is
measurement — the planned comparison benchmarks these indexes against pgvector
*and publishes the result including where Postgres wins*. The risk of getting
worse numbers than the off-the-shelf option is accepted and owned there.
