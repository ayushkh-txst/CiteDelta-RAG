# ADR-0001 — Postgres as the job queue substrate

**Status:** Accepted · **Date:** 2026-08-08

## Context

Ingestion must survive worker loss, retry with backoff, and dead-letter poison
inputs.

## Decision

Implement the queue as a `jobs` table in the same Postgres database as the
domain data, claimed with `SELECT … FOR UPDATE SKIP LOCKED`.

## Alternatives

- **Redis / RQ** — fast, but job state and the writes the job performs live in
  different systems. Every crash between "wrote the chunks" and "marked done"
  is a dual-write bug to design around.
- **SQS** — managed and durable, but the spec's whole point is that nobody
  interviews you on a queue you configured.
- **Celery** — imports the semantics instead of defining them; I could not then
  explain the visibility-timeout behaviour precisely, which is the value here.

## Consequences

**Positive.** Enqueue participates in the caller's transaction, so "write these
rows and schedule the follow-up" is atomic. One system to operate and back up.
The claim query doubles as crash recovery, so there is no reaper to deploy.

**Negative.** Throughput ceiling in the low thousands of jobs/sec. Polling costs
idle queries (`LISTEN`/`NOTIFY` is the fix if it matters). Long-running jobs
holding transactions interact badly with autovacuum. None bind below ~10⁵
jobs/day; past that, an outbox pattern plus a real broker.
