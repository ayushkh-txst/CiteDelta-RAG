# ADR-0003 — Dead letters are a `state`, not a separate table

**Status:** Accepted · **Date:** 2026-08-08

## Context

Jobs that exhaust `max_attempts` need to stop being claimed and become visible
to an operator. The simplest shape is a separate `dead_letters` table.

## Decision

Keep one `jobs` table and model dead-lettering as a `state` value (`dead`),
alongside `queued`, `claimed`, and `succeeded`.

## Alternatives

- **Separate `dead_letters` table.** Cleaner separation of concerns, but
  requeuing means moving a row, every history query joins two tables, and there
  are two places to look for a job's past.

## Consequences

**Positive.** Requeue is a one-column `UPDATE`. A job's entire history lives in
one row with one `attempts` counter. The hot claim query keeps its `WHERE
state IN ('queued')` predicate, so dead rows are invisible to it.

**Negative.** The hot table carries terminal rows forever, so the table grows
and the `queued` predicate must stay partial-indexed to remain cheap. Revisit
at 10M rows, where an archive table becomes the honest move.
