# ADR-0002 — `attempts` increments at claim, not at failure

**Status:** Accepted · **Date:** 2026-08-08

## Context

A worker that is killed with `SIGKILL` never reports failure — the OS takes the
process and the transaction rolls back, so nothing runs the "record a failure"
path. If attempts only increment on an explicit failure, a job that reliably
kills its worker is retried forever.

## Decision

Increment `attempts` at claim time, atomically with the claim, not when the job
is later marked failed.

## Alternatives

- **Increment at failure.** Clean bookkeeping, but `kill -9` leaves no record —
  the poison job loops forever and takes a worker down each time. Rejected.
- **Heartbeat + timeout.** More accurate blame, but it is a second liveness
  mechanism to build, tune, and explain for a corpus of a few hundred jobs.

## Consequences

**Positive.** A crash still burns an attempt, so a job that reliably kills
workers reaches the DLQ instead of killing them forever. Claim is one atomic
`UPDATE … FROM … RETURNING`, so there is no read-then-write race.

**Negative.** A job lost to an infrastructure blip (not its own fault) also
burns an attempt, so `max_attempts` must be set with that in mind — set too low
and healthy jobs die to a network flap. A claim followed by an immediate
rollback double-counts; accepted because retries, not accounting, are the goal.
