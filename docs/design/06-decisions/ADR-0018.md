# ADR-0018 — Query traces store candidates as JSONB

**Status:** Accepted · **Date:** 2026-08-11

## Context

The trace panel needs every fused candidate, including uncited ones. That data
is unrecoverable after the query — the retriever's ranking is gone once the
request completes, so it must be persisted at request time or never.

## Decision

One `query_traces` row per query, candidates as a JSONB array, a CHECK
constraint enforcing answer XOR refusal.

## Alternatives

- **A normalized `trace_candidates` table** — a join on the read path and N
  inserts on the write path, in exchange for referential integrity between
  rows that have no independent lifecycle. Rejected.

## Consequences

**Positive.** Reads are one row; the trace panel does a single fetch. The full
fused list survives, including candidates the model chose not to cite — which
is exactly the "shown and not used" distinction the trace exists to make.

**Negative.** Cross-trace analytics are awkward — "which chunks are retrieved
often but rarely cited?" is a genuinely useful retrieval-quality question and
JSONB makes it clumsy. Revisit if that question becomes routine.
