# ADR-0013 — Bounded work under a filter

**Status:** Accepted · **Date:** 2026-08-11

## Context

With a very selective filter the stopping rule never fires: the search keeps
revealing candidates waiting to accumulate k admissible rows. Unbounded, a
query at 0.5% selectivity walks essentially the whole graph — the sweep
measured 10,728 positions visited at s=0.005%. One hot query dominates a
request path, and a latency guarantee on the unfiltered path becomes a gamble
on the filtered one (ADR-0011's "fixed cost becomes data-dependent").

## Decision

Both filtered indexes carry explicit work budgets, implemented as limits not
heuristics:

- HNSW: `max_visits` — an upper bound on pool insertions during the layer-0
  search, reported via the `last_visits` property.
- IVF: a probe ceiling — filtered search probes at most `floor * nprobe` cells
  (a bounded multiple of the configured floor) seeking k admissible rows.

Exceeding the budget does **not** raise: the search returns the best results
found so far, and the retrieval trace flags the query as **degraded**.

## Alternatives

- **Unbounded search** — a single query can walk the entire graph; rejected.
- **Hard failure** — a degraded answer with a warning beats no answer at all
  for a compliance product; rejected.

## Consequences

**Positive.** Tail latency is bounded by policy, not by luck. Recall is traded
for p95 deliberately and measurably, and the budget is *config*, so the
recall-vs-tail-latency trade is an operator's call rather than baked in. The
trace makes degradation explicit — the same trace that powers the future
inspector panel.

**Negative.** Recall becomes budget-dependent, so any reported recall figure is
meaningless without its budget. Best-effort results can still be returned
without the user being told how degraded they are unless the caller reads the
trace. Budget ceilings can mask a genuinely bad filter as "just slow".
